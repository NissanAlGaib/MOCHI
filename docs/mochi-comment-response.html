A9 — N-grams instead of unigrams

A9 Use N-grams instead of unigrams to capture context better Implemented

"Use N-grams instead of unigrams (1-grams) to capture context better."

Partly already in place. The classification models already used word bigrams and character 3–5 grams. The gap was in the statistical analysis script, which tested single words only — that is likely what was seen.

N-gram support was added there, with the unigram default preserved so every previously reported figure stays reproducible.

N-gram ablation · 82,765 samples

The comment is supported, but not by the statistic one would expect. Peak Cramér's V does not move at all. That is not evidence against n-grams — V is a symmetric association measure that penalises rarity, and every bigram is rarer than its parts, so V structurally cannot rise.

What improves is contamination: the share of a term's occurrences that fall on benign text, which is the false-positive rate that term would produce if promoted to a detection rule.

previous                4,184 malicious /  746 benign    15.1% contaminated
previous instructions   2,439 malicious /    9 benign     0.4% contaminated

Same phrase family, an 83× cleaner indicator, and a lower Cramér's V (0.198 vs 0.211). Reporting V alone would have hidden the entire finding. This is also precisely the distinction the rule-based stage already hand-codes, so the analysis now agrees with the detector.

Recommendation: n = 1–2, not 1–3. Trigrams add 11,568 terms and make contamination marginally worse.

A10 — Word cloud

A10 Create a Word Cloud for data visualization Implemented

"Create a Word Cloud for data visualization."

Three figures produced. Terms are sized by |log-odds|, not raw frequency — a frequency-weighted cloud of any English corpus is a picture of the stopword list and carries no information about the label. A side-by-side panel showing both weightings is included so the choice is visible rather than asserted.

The figure then did more than illustrate. It surfaced a corpus problem the token tables had not made obvious.

Finding — the corpus rewards shortcuts

14 of the 150 strongest malicious-associated terms are artifacts of how the benchmark was built, not attack language: pwned (2,789 malicious / 0 benign — a benchmark success marker), kermode, kermodei, gribbell, ursus, americanus (one reused source article), few_shot_examples, name_1 (a template placeholder).

Beside them sits a block of Spanish: gracias, esta, volvi, libro, biblioteca, hola, gusta, donde, clave, por, sido, negro, secreta.

The corpus does not merely contain benchmark markers — it teaches that non-English text is malicious. A classifier can score well on this without learning anything about prompt injection, which is the empirical argument for semantic detection over keyword matching. It also makes A14 a requirement rather than an enhancement.

A11 — Feature engineering

A11 Perform feature engineering by adding new useful columns Implemented

"Perform feature engineering by adding new useful columns to the dataset."

73 columns across nine families: surface, punctuation, imperative structure, injection lexicon, obfuscation, language, URL, position, and identity. Roughly 25 of them were already being computed on every request and discarded — the obfuscation flags in particular — so materialising them was bookkeeping rather than new analysis.

One design rule governs the whole thing: features are defined in one module, which both the dataset builder and the live gateway import. A notebook that recomputed a column its own way would drift from the running system, and every ablation number would quietly become fiction with no test failing.

Ablation — do the engineered columns add anything?
VariantPrecisionRecallF1FPRFeatures
TF-IDF only (control)0.73780.63280.68130.1224200,000
Engineered only0.52910.62280.57210.301771
TF-IDF + engineered0.74020.76710.75340.1466200,071

Adding 71 columns to 200,000 lifts F1 by +0.0721 and recall by +0.134 at essentially unchanged precision — the engineered features catch attacks the bag of words misses entirely, which is what the obfuscation family was predicted to do. This also overtakes the previous best classical model.

The cost is false positives: 0.1224 → 0.1466. Both remain an order of magnitude above the <1% requirement, so neither is deployable as a front-line filter, and the features remain analysis-only until the semantic stage exists to compare against. Wiring an unvalidated signal into a security decision path is how a false-positive rate regresses unnoticed.

A12 — Keyword dictionary and question marks

A12 Detect adversarial commands via a keyword dictionary and question marks Implemented

"Detect adversarial commands by building a dictionary of common prompt injection keywords and tracking question marks."

The dictionary already existed and was not rebuilt: 61 regular expressions across 9 detector categories, externalised to a configuration file so patterns are revisable without code changes. It was extended rather than duplicated.

The question-mark idea was new and, importantly, testable. It was implemented as measurable columns rather than assumed — the hypothesis being that benign users ask while injections command.

Measured across all 82,765 samples                           benign    malicious
question_ratio            0.1156       0.0435
ends_with_question        0.1287       0.0327   3.9×
imperative_verb_count      0.3775       1.4179   3.8×
starts_with_imperative     0.0502       0.2007   4.0×

The hypothesis holds. Benign prompts are roughly four times more likely to end in a question mark; injections carry roughly four times the imperative verbs. This is now a measured claim rather than an assumption, and it is reported with the caveat that it may partly reflect how the benchmark corpora were assembled.

A13 — LSTM and GRU comparison

A13 Compare model performance against LSTM and GRU Deferred, not declined

"Compare model performance against LSTM and GRU."

Accepted, and deliberately sequenced after the semantic model is trained rather than before. The proposed model's weights do not yet exist — the code is complete but has never been trained. Comparing recurrent baselines against an untrained model would produce a table with a hole in the row that matters.

The plan is written and the phase is scheduled. Six rungs on one ladder, in increasing capability: rule-based → naive Bayes → linear SVM → BiLSTM → BiGRU → the fine-tuned transformer, all on identical splits with a recorded seed.

Latency and parameter count will be reported beside F1. MOCHI is a gateway with a response-time budget, not a leaderboard entry; a recurrent model that lands within a point or two of the transformer at a fraction of the memory is a genuine finding and belongs in the discussion rather than being buried for losing on one metric.

One scope note

The ladder is capped at a single table. The risk in this phase is a systems thesis drifting into a model-comparison thesis because the comparison turned out to be interesting.

A14 — Code-switching

A14 Address code-switching by normalizing mixed languages Detection built · validation outstanding

"Address code-switching by normalizing mixed languages in the prompt before prediction."

Scoped to English–Tagalog only, as instructed. The mechanism was changed, and that change is the first thing to raise.

Mechanism substituted — please confirm

The comment asks for normalising mixed languages before prediction, i.e. translating to English first. That was not adopted, for two reasons:

1. It spends the latency budget. A translation call sits inside the request path, on a system whose central claim is sub-millisecond first-stage filtering.

2. It is itself an attack surface. A translator can drop or introduce instructions, and the detector would then be judging text that no attacker ever sent.

Instead, language is identified and recorded as a signal, and Tagalog attack patterns were added directly. The semantic encoder already in use is a multilingual model, so no translation step is needed for it to read Taglish.

The gap that was found

Before this work, measured against code-switched test cases:

                     attacks blocked
taglish_attack            0 / 11
tagalog_attack            0 /  7
english_attack              3 /  4

Every Tagalog and code-switched injection passed the first stage untouched. The existing mixed-script check could not see it either — Tagalog and English are both written in Latin script, so it reported "not mixed" for all of them. Script and language are different questions, and only one was being asked.

After

taglish_attack           11 / 11        taglish_benign    12 / 12 pass
tagalog_attack            7 /  7        tagalog_benign     6 /  6 pass
english_attack            4 /  4        english_benign     4 /  4 pass

No regression on the English corpus. Re-running the full evaluation over all 82,765 rows gives byte-identical results — precision 0.97284, recall 0.05896, false-positive rate 0.00126, every figure unchanged. The Tagalog patterns require Tagalog tokens, so they are inert on English text. New coverage at zero cost to the false-positive requirement.

A pre-existing English gap was also found by the control row and fixed in the same pass: a common persona-reassignment phrasing had never been caught.

Limitation — this is why A14 is marked partial

The Tagalog test sentences, word lists, and patterns were all generated by a language model. No dictionary, translation tool, published corpus, or Tagalog speaker was consulted.

The fluency risk is real but secondary. The structural problem is that the detector and its test set share an author: the sentences use exactly the vocabulary the word list contains, so the perfect score measures internal consistency, not detection. Real Tagalog will use words the list has never seen.

This also means proofreading the file does not fix it — the replacement set must be written independently, by someone who has not seen the word list, or the same circularity is reproduced with a human signature on it.

No figure from these fixtures should appear in the results chapter. The 82,765-row no-regression result above is unaffected by this and stands on its own.

Proposed remedy

Two things, separable because they need different evidence. Attack samples can legitimately be synthetic — collecting real injections against production systems is not ethically available, and this is the same attack-simulation protocol already approved for the obfuscation evasion tests. What they need is independent authorship: the two co-researchers each write 25 attacks and 25 ordinary requests without reading the word list.

Language identification is different and does not need synthetic data at all. It can be validated against ordinary published Tagalog text, which requires no injection labels and exists already. That converts the weakest claim into a real measurement.

Decisions needed

Four points where the work is blocked on a call that is yours rather than ours.

  1. spaCy or NLTK? This was raised previously and is still open. It has become blocking rather than merely pending: the imperative-structure features in A12 are currently word-list based, and starts_with_imperative is genuinely approximate without part-of-speech tagging — it cannot separate "Ignore the previous instructions" from "Ignoring the noise, the result holds." Numbers are already being reported from this family.
  2. Is the A14 mechanism substitution approved? Language identification as a recorded signal, rather than translation before prediction. The reasoning is above; if translation is preferred despite the latency and attack-surface costs, it can be built instead.
  3. Is the synthetic-attack methodology acceptable for the code-switching evaluation, given independent authorship and hold-out, and reported separately from corpus-derived figures? This mirrors the attack-simulation protocol already in the approved design.
  4. Confirm A13 sequencing — recurrent baselines after the semantic model is trained, not before, and capped at one table.
